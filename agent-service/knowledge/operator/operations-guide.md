# PrizeFlux 运营操作指南

## 审核个人活动

在运营审核工作台查看待审活动，检查活动时间、每日参与限制、奖项名称、库存和概率配置。审核通过前，普通用户的草稿不会进入公开活动目录。驳回时应填写具体、可执行的原因；创建者可以按原因修改并重新提交。通过审核会发布并冻结活动配置，若需变更应使用新的合规业务流程，不直接修改已发布规则。

## 平台内活动管理

运营账号可以在运营活动页管理由平台运营创建的活动。发布前确认时间、奖项、库存和概率配置；发布后不可直接改写已公开配置。关闭活动会停止新的参与，不会删除已产生的参与记录或抽奖结果。

## 理解抽奖与排队状态

概率总和小于 1 时，剩余概率表示未中奖；概率不代表一段时间内的确定性承诺。排队模式用于把高峰请求异步化，“已受理”不是中奖或奖品预留的承诺。MySQL 中的最终请求、库存、次数和结果是业务事实；Redis 只辅助限流/流量治理，Kafka 用于任务传输与缓冲，消息重复不应成为重复扣减的理由。

排队状态 `QUEUED` / `PROCESSING` / `RETRY_WAIT` 分别表示等待、处理中和等待系统重试；`COMPLETED` 才有最终抽奖结果。`MANUAL_REVIEW` 表示请求被保留并停止自动重试，应按查询标识和业务状态码进入人工核查，不要通过新增请求或直接修改数据库来补做。`REJECTED` 表示该请求没有完成抽奖；先确认活动状态、参与资格和限流提示，再决定是否在产品允许时重新发起。

排查队列延迟时，区分“入口已受理”与“抽奖已终态”：检查积压数量/年龄、队列状态、Outbox 发布确认、Worker 处理/重试与库存和结果账本是否对齐。Kafka 暂不可用时先查看持久队列和 Outbox 是否恢复，不手工改库存、开奖结果、消费 offset 或 Outbox 状态；监控栈不可用时记录请求标识与时间，避免把仪表盘空白误判为零积压。

## Agent 助手

Python 活动助手通过当前登录令牌委托 Campaign 服务验证身份，按服务端角色和活动归属执行受限只读查询。公开帮助可供普通用户检索；本运营手册只允许 OPERATOR 检索。助手只能解释和查询，不能代替运营员审核，也没有活动写入、发布、抽奖或库存工具。

## Fake 与外部模型

Fake Model 用于离线验证 Agent 控制流程，不代表真实模型质量，也不一定查询活动事实。外部兼容模型只有在本机明确配置后才会发出模型请求，并可能产生供应商费用。外部模型输出仍是不可信文本；规则、身份、状态和操作权限由服务端代码决定。

## 数据与隐私

会话、运行状态和知识索引属于 Agent 自己的存储边界。访问权限应在检索时根据服务端身份决定，不能采信用户或模型传入的角色字段。文档撤回后，检索必须重新核对 MySQL 权威元数据，不能仅凭 Qdrant payload 放行。不要把用户的私人活动内容或抽奖记录导入共享知识库。
