# PrizeFlux Vue 3 前端构建计划

状态：2026-09-28，依据用户反馈改为“成熟开源方案优先”，不再从空白处自创整套视觉。当前已运行功能与 API 契约不重写；按参考项目的页面结构与组件约定分批实现、验收。

## 目标

把 PrizeFlux 做成面试官可以实际操作、使用者能快速理解的活动抽奖产品界面。用成熟 Vue 3 开源设计系统解决基础布局、表单、状态、导航和响应式问题；只保留最少的 PrizeFlux 品牌识别，不再自创大幅科技插画、轨道图形或认证宣传区。登录、参与活动和处理审核等任务应先于技术介绍，不更改服务端权限、库存、幂等、抽奖或 Agent API 行为。

## 开源参考与采用边界

- **主参考：[`pure-admin/vue-pure-admin`](https://github.com/pure-admin/vue-pure-admin)**。截至本次调研，仓库约 20.6k stars，MIT 许可；README 明确采用 Vue 3、Vite、Element Plus、TypeScript，并标明兼容移动端。借鉴其认证表单、工作台导航、表单/表格层级和断点策略。
- **组件基线：[`element-plus/element-plus`](https://github.com/element-plus/element-plus)**。Vue 3 组件库，MIT 许可。对表单、按钮、卡片、提示、表格等优先使用成熟组件，不再用零散原生样式模拟控件。
- 不整仓复制或替换成 Pure Admin 脚手架，不照搬品牌、图标、图片、假账号或演示数据；不从 README 截图反向拼画面。业务 API、权限、真实状态和数据仍由 PrizeFlux 决定。新依赖只引入确实使用的组件，继续检查包体积与无障碍。

## 设计原则

1. **先完成用户任务**：每页首屏有清楚标题、当前状态和主要操作；登录表单不能被大幅产品介绍推到首屏之外。
2. **一个连续的产品画布**：登录/注册属于同一认证场景，不做上下两块互不相干的“宣传页 + 表单页”。宽屏可在同一背景和同一视觉容器内采用双栏；窄屏先表单，产品链路缩为紧凑说明带或置于表单之后。
3. **围绕真实业务表达品牌**：用“身份校验 → MySQL 事务开奖 → 中奖后 Outbox/Kafka 履约”的路径作为识别元素，不用虚构用户数、中奖信息、活动或外部人物素材。
4. **可读性优先于装饰**：正文约 16px；表单标签、按钮和重要状态至少 15px；辅助信息至少 13px。更小文字只用于非交互、非关键信息的装饰性编码；任何业务说明不得以微型等宽字呈现。
5. **沿用成熟模式，不造控件**：组件视觉和交互以 Element Plus/Pure Admin 已有模式为准；页面内容按用户/运营/Agent 角色分工，不为“科技感”添加无业务含义的图形、迷你文字或装饰卡片。
6. **响应式与无障碍同时验收**：键盘焦点清晰；跳过导航；表单有可见标签和错误；状态变化可被辅助技术读出；尊重减少动态效果；窄屏无横向溢出。

## 页面结构与用户路径

```text
未登录：品牌入口 → 登录 / 注册 → 活动目录
普通用户：活动目录 → 活动详情 → 即时抽奖 或 排队 → 结果 / 我的记录
普通用户：我的活动 → 编辑草稿 → 确定性校验 / Agent 建议 → 提交审核
运营人员：待审核 → 查看规则与奖品 → 批准 / 驳回并说明 → 活动管理
运营人员：活动助手 → 授权只读查询 / 知识来源 → 运行状态 / 取消 / 继续
```

页面责任：

- **登录/注册**：复用一个认证壳和同一张表单卡片；不把“产品介绍”和表单拆成两块主视觉。品牌说明保持一行，链路说明放回产品主页/项目介绍。手机首屏显示标题、用户名、密码和主按钮；字段提示贴近字段。
- **活动目录**：标准内容页标题、真实活动列表、开放状态和明确的详情入口；加载、空态和错误态均使用组件库模式，不以主视觉或装饰图案替代活动内容。
- **活动详情/抽奖**：规则、奖项/概率、资格和操作区层级清楚；即时与排队是显式两种路径；等待中提供状态与手动刷新；不得暗示客户端结果权威。
- **我的记录**：结果和时间可扫读；中奖、未中奖、库存耗尽、处理中/履约状态使用文字标签和颜色共同表达。
- **创作者工作台**：草稿状态、编辑内容、校验结果和提交审核的下一步清晰；Agent 只给建议，保存仍由用户操作。
- **运营审核**：队列列表、选中项详情和决定区分组；批准/驳回的后果及驳回理由一目了然。
- **Agent 助手**：Fake/真实模型身份明确；用户问题、工具轨迹、检索来源、运行状态与继续/取消边界分层；不伪装成通用聊天框。

## 分批实施顺序

### F0：信息架构与现状盘点

- 对照当前 Router、API 客户端、各 View、已有组件测试，列出页面/角色/主要操作与状态。
- 记录当前产品入口与视口基准；保留已实现业务行为，不为视觉改版重做 API。
- 输出本计划及清楚的页面验收项。

### F1：接入成熟组件基线与认证壳

- 将 Element Plus 作为 Vue 3 控件基线，先接入表单、按钮、卡片和提示；尽量用组件默认交互与 token，不再堆叠相互冲突的 CSS override。
- 先重做登录/注册：一个复用认证壳、一张主表单卡片；删除认证页上的大幅链路介绍，让认证操作成为唯一主任务。
- 页面全局基础层级参照 Pure Admin 的 app shell 与内容容器，拆分为后续 F2/F3 批次，不在这一批重写业务逻辑。

### F2：用户参与链路

- 已收整活动目录与详情：采用 Element Plus 内容页、卡片、按钮、标签、提示和骨架屏；移除自绘首页插画、详情票券和抽奖圆盘，不改 API 与业务状态逻辑。
- 个人历史记录已改用组件库活动记录卡、结果标签、加载/空态与错误提示；不展示非权威履约字段。
- 对队列等待、拒绝、完成与中奖/未中奖逐一检查文案，保留服务端权威与幂等语义。

### F3：创作者与运营工作区

- 统一我的活动、草稿编辑、校验建议、待审核与运营活动页。
- 审核/发布等高影响操作突出对象、结果与原因；窄屏切换为可读纵向流，不压缩为小字表格。

### F4：Agent 工作区

- 清楚呈现模型模式、会话、run 状态、工具/知识来源和取消/恢复动作。
- 错误与空状态提供用户可执行的下一步；真实模型和检索未启用时准确标示，不制造示例结果。

### F5：整体验收

- 前端测试与生产构建；关键交互与权限回归；桌面与窄屏实屏检查。
- 视口至少覆盖 1440×900、768×1024、390×844、320×720；重点页面无横向溢出。
- 认证页 390×844 首屏必须能看到用户名、密码、主操作，不先滚过大幅说明区；所有可交互控件触控/点击目标尽量不小于 44×44 CSS px。
- 核对正文字号、对比度、键盘焦点、表单错误/成功提示、减少动态效果与空/错态。
- 只有本机真实运行且通过的行为才记录为运行验收；不据自动化测试宣称浏览器/公网发布完成。
