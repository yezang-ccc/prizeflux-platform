# PrizeFlux 可维护性约束与技术债

日期：2026-09-30。用户要求按资深工程师的标准完成项目。本文件记录可检查的工程约束和当前技术债，不是对全仓质量的认证；完成状态以交接记录、源码和实际验证为准。

## 每批改动必须回答的问题

1. 改动解决什么已观察到的问题，为什么属于这个模块？
2. 是否复用已有用例/端口/DTO？新增抽象处理哪个实际变化点？
3. 数据、权限和事务的权威边界有没有变化？超时、重试、取消和进程退出时发生什么？
4. 对应的成功/失败路径如何验证？性能结论绑定哪个环境和具体构建文件？
5. 哪些事项仍未验证，下一位接手者可以从哪里继续？

## 责任边界

| 部分 | 应承担的责任 | 应避免的耦合 |
|---|---|---|
| Java controller | 鉴权后的HTTP输入/输出和安全错误契约 | 直接改库存、发送消息、执行模型 |
| Java application/domain | 活动/审核/抽奖用例、幂等事务和业务规则 | 让Redis/Kafka/前端成为业务事实 |
| Java infrastructure | JDBC、Redis、Kafka、遥测和运行装配 | 把供应商或指标失败变成已提交业务的回滚/重试 |
| Python Agent | 有界运行、身份委托、只读工具、证据/报告和持久生命周期 | 复制Java权威校验、参与审核/开奖/扣库存 |
| Vue | 用户交互、授权页面、显式提交和结果展示 | 把隐藏按钮当权限控制、把模型建议当服务端判定 |
| 隔离验证工具 | 创建合成环境、运行场景、记录原始结果、限定清理目标 | 混入产品凭据/数据、无界并发、隐式全局依赖 |

## 本轮已落实的改进

- Kafka lag采样独立于共享scheduler，并用一个在途任务限制后台工作；所有scrape只读缓存。相关单测覆盖慢broker、失败缓存和中断，真实Embedded Kafka覆盖commit前后lag。
- Kafka发送与等待确认分别计时；遥测故障不改变已确认投递。Relay在发送中断后停止本批，剩余记录由既定lease协议恢复。
- Prometheus解析和Campaign采样从主smoke脚本抽出到`CampaignRuntimeMetrics.psm1`，显式接收BaseUrl与Headers；主脚本保留环境/场景编排。离线合同检查覆盖多client、缺失/非有限值、标签顺序、URL、部分抓取和超时。
- 到达率实验记录源码commit/dirty文件数、Campaign/Worker JAR、主脚本与采样模块的SHA-256；历史JSON保留原样。用这些信息绑定实际运行内容，而不是以历史CI代替当前工作树验证。
- 协作规范已加入上述可维护性要求，后续Agent也必须遵守。
- Relay并发生命周期拆到 `BoundedOutboxDispatcher`，业务Publisher继续做领取、逐事件确认/重试及围栏回写。默认串行；可选最多8线程、领取一波、整波join/15秒等待，超时停止后续领取。取消不宣称能强杀JDBC，旧任务仍受原token围栏；需重启/其他Relay回收未决租约。失败事件用既有 `available_at` 做2秒起、30秒封顶的指数退避，避免100ms轮询把重试次数消耗在Broker恢复窗口；最大尝试仍会死信，需处理。候选三轮50 RPS×5分钟和一轮Kafka停机恢复已有单机证据，边界见基准记录。

## 已确认的技术债与处理顺序

| 项目 | 影响 | 当前决定 |
|---|---|---|
| 主smoke脚本仍接近两千行，混合性能/故障/备份等历史路径 | 修改与复核成本偏高；160行采样模块抽取只处理了其中一个职责 | 新采样不再加回主脚本。后续按环境生命周期、场景执行、结果对账拆分；每次保持相同输入/输出和随机环境清理协议，不一次性重写所有路径 |
| Campaign/Worker的Kafka Admin lag读取实现相似 | 两个部署单元可能分别演进，修复需要核对双方 | 当前保持服务独立；不通过Campaign↔Worker依赖或把Kafka放进Contract来去重。若共同需求稳定，再考虑专门的基础设施复用模块 |
| 旧计划/资料含已被新证据覆盖的描述 | 接手者容易把历史状态当当前状态 | 以PROJECT_STATUS顶部和最新原始证据为准；发布材料在R阶段统一核对，不删除历史失败或私有学习记录 |
| 50 RPS性能目标尚未达到，真实RAG/模型评测及发布证据未闭环 | 不能证明产品最终竞争力或生产容量 | 先定位J2/J3，再回归新失败窗口，之后推进已批准K/Q/R路线；避免用新增框架掩盖现有不足 |

## 合并/发布前的退出要求

- 核心业务的库存、幂等、权限、消息重复和lease/fencing验证通过；新失败窗口有对应检查。
- 关键配置有默认值、有效范围、失败行为及回退方法；后台执行有生命周期管理。
- 相关定向测试通过，里程碑末集中回归；源码、迁移、接口和部署合同兼容。
- 差异没有无关重命名、未解释的依赖或重复权威规则；`git diff --check`通过。
- 简历与文档只引用实际证据；密钥、私人学习材料和真实运行配置按既有发布边界处理。
