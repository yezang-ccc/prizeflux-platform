# ADR-002：抽奖以 MySQL 约束为最终防线

状态：D4 架构决定，2026-09-23。实现和集成测试尚待完成。

## 决定

活动 V1 不改写，D4 从 V2 迁移增加配置版本、奖品库存、请求、结果、业务次数和 Outbox。概率在发布边界被限定为六位小数；数据库字段为 `DECIMAL(7,6)`，可表达 `[0,1]` 全区间。奖品总概率不超过 1 属于跨行规则，在发布事务中锁定版本并校验；单行 CHECK 无法单独保证。

业务请求键唯一范围为 `(operation, user_id, request_key)`。保存 32 字节请求指纹，同键不同指纹拒绝；数据库唯一约束解决并发抢占，应用层在冲突事务结束后重读赢家结果。一个请求唯一对应一条结果。未中奖与售罄结果也持久化；获奖结果同时写 Outbox，失败时整体回滚。

实时库存存在 `prize_inventory`，条件更新必须带 `remaining_stock > 0` 且检查受影响行数；CHECK 防止其他写路径直接写入负数。业务日次数存在 `user_campaign_quota`，以联合主键和条件更新控制上限。Redis 预占、缓存或入口限流不替代这些数据库不变量。

Outbox 允许至少一次发送：租约、领取标识、可重试时间、次数和状态持久化。Worker 侧另用 `eventId` 和 `drawId` 两层去重。外部供应商发奖需要自身幂等键或查询能力，不能仅从本库约束推导一次性外部效果。

## 后果与验证

同一活动热库存行可能成为瓶颈；先取得正确性与性能基线，再用 Redis 优化入口流量。下次 MySQL 里程碑集中验证迁移可执行、重复键被拒绝、负库存与非法状态被拒绝、事务失败不留下结果和事件，以及并发不超卖。只有 SQL 文件存在不能把 D4-01 标记完成。
