## K2 面试深挖：为什么 Embedding 不能只写一个模型名

**具体问题：** 原有 RAG 管道有 mock/HTTP 端口，但没有可复现的本地语义向量。若索引构建和在线查询使用不同权重、维度或 query 前缀，检索会静默退化；若启动时按模型名隐式下载，又引入网络/供应链/成本不确定性。

**本批实现：** 选定 MIT 许可的 BGE 中文小模型与固定 Qdrant ONNX commit；7 个模型文件逐一 SHA-256 校验，512 维及 query instruction 进入模型 revision。构建和在线检索共用一个 provider factory，原 HTTP 合同不变；FastEmbed 只从绝对本地目录读取，显式下载命令与运行时分离。专用单线程 CPU executor、单在途门闩和输入批次上限避免无界并发。

**可讲证据与边界：** Python 3.14.6 Windows 本机真实推理返回 512 维、范数1；148个非MySQL Agent 测试、Ruff/mypy通过。约0.85秒是一次冷启动+单查询，不是P95；Docker可选镜像构建因容器访问PyPI TLS EOF未验收，Qdrant active index/真实召回率未测。现在可讲“可复现/可审计的本地 Embedding 接入”，不能在简历写“RAG上线”或“检索质量提升”。取舍与来源见[K2决策](../architecture/local-embedding-k2.md)。

## 2026-09-30 新增难点：观测链路也可能干扰被测链路

**可讲的问题：** 50 RPS时入口较快而结果延迟约51秒，为什么不直接加线程或连接池？已有实验加连接池/消费者/活动分散未改善，需要继续分开发送、提交和业务处理的成本。

**已经实现：** 在Outbox传输中区分`KafkaTemplate.send()`与future确认等待，保留既有Outbox总体/创建到确认计时；采集每个consumer client的原生commit时延、提交数和排队topic/group committed lag。真实Embedded Kafka证明“消息已读”不等于“offset已提交”：读取两条记录后lag仍为2，提交后才为0；发送Timer及commit指标实际可导出。

**工程取舍：** lag查询不放在Prometheus scrape或运行Outbox的共享scheduler里，而用独立线程、最多一个在途任务；broker慢时跳过重复触发，失败保留旧值并标记新鲜度。否则为诊断而添加的Admin超时，可能反过来拉低Relay吞吐。指标错误不会改变已确认投递；发送中断停止本批，余下租约可恢复。

**面试边界：** 当前只有接线与5类16项定向验证，本轮Docker未运行，尚无新50 RPS数据；不能说已定位Kafka为根因，或已提升到多少QPS。原生commit均值是每client滚动窗口的毫秒数，发送Timer是秒，二者都不能冒充端到端P95。下一轮以同配置重新测量，形成可证伪假设后再优化。可以描述这套定位方法与可靠性保护，暂不在简历写优化百分比。

## 一、项目该怎么讲

PrizeFlux 是个人项目（AI 辅助开发），分成两条可以分别投递、但共享产品背景的技术主线：

1. **PrizeFlux 抽奖平台后端**：并发抽奖的业务正确性、排队准入、MySQL 权威状态、Redis 流量保护、Kafka 通知和 Outbox 可靠投递。
2. **PrizeFlux Copilot / Agent Harness**：Python FastAPI 服务，使用 LangGraph 控制模型—工具循环；项目自己实现身份委托、只读工具授权、调用预算、持久运行、取消/租约、SSE 和检索证据约束。

面试时不要把“用了 Kafka/Redis/LangGraph”当成亮点本身。要讲清楚：保护了什么不变量、遇到什么瓶颈、怎样设计可重复实验、数据怎样变化，以及仍然有哪些限制。

**60 秒项目概述（按应聘方向选择重点）：**

> 我做了一个活动抽奖平台，Java 后端负责活动和抽奖，MySQL 是库存、抽奖结果和排队任务的最终事实源。同步入口完成身份与限流校验后，把排队请求和 Outbox 事件放在同一事务提交；Kafka 只负责唤醒异步消费者，数据库状态与恢复扫描保证业务正确性。为了评估而不是猜测系统能力，我搭了隔离的 k6 开放模型压测，记录入口延迟、受理到终态延迟、积压、资源和最终账本对账。25 RPS×5分钟、Outbox 间隔1秒、消费者并发4的三轮同机复测均通过，端到端 P95 在2.52～3.04秒；50 RPS×60秒多轮探索均未过性能门槛，调大连接池、消费者并发、分散活动后处理速率仍低于到达速率。我保留失败结果并停在边界，没有把最终排空/数据正确说成性能达标。以上仅限同机实验，不外推生产容量。

## 二、异步抽奖链路与正确性边界

```text
USER 请求
  → Campaign 身份 / Redis 限流 / 队列容量保护
  → MySQL 事务写入排队请求 + DrawQueued Outbox
  → Outbox Relay 发布 Kafka 通知并记录发送结果
  → Campaign Kafka 队列消费者唤醒待处理任务
  → MySQL 事务竞争领取并执行抽奖、扣库存、保存结果与终态
  → 后续中奖履约事件交给独立 Worker
```

- **MySQL 是业务真相**：抽奖请求、参与次数、库存扣减、中奖结果及其业务终态不能以 Redis 或 Kafka 消息作为最终凭据。
- **Kafka 消息是异步唤醒/传递机制**：消息可重复、延迟或暂时不可用；消费者必须回到数据库确认任务状态，并使用行锁/状态条件和幂等语义避免重复执行业务。
- **Outbox 解决数据库与消息系统双写**：业务行与待发布事件在同一个 MySQL 事务里提交。Relay 后续发布；失败保留可重试状态，不能出现业务提交成功但永远没有可恢复通知的窗口。
- **Redis 用在入口保护**：Lua 限流支持跨实例原子计数，过载保护用于拒绝或降速。它不做库存最终扣减，不代表“Redis 让抽奖更快”。
- **抽奖与履约是不同阶段**：队列处理活动业务；独立 Worker 负责中奖后履约。测试中的履约适配器是模拟实现，不要说成真实供应商已接入。

## 三、已记录的 25 RPS 调优实验

### 实验目的与口径

使用 Grafana k6 的开放模型 `constant-arrival-rate`，按计划速率持续产生请求，而不是等上一个请求结束才发下一个。场景先低速预热 30 秒，再以 25 请求/秒测 60 秒；Campaign 的队列消费者和 Worker 从预热前在线。服务、k6、Docker 依赖和数据库/队列监控都在同一台 Windows 主机，数据服务使用隔离的一次性容器，结束后清理。

- **入口 P95/P99**：排队 HTTP 请求被服务端受理的耗时。它短，只说明请求入队快。
- **端到端 P95**：从请求受理到队列任务变成业务终态的耗时。它更接近用户“等到结果”的体验。
- **dropped iterations**：生成器未能按计划启动的迭代；不是服务端成功或容量指标。
- **业务对账**：将请求受理数、MySQL 队列行及终态、抽奖/库存、Outbox 已发送数、Worker 账本等核对；只看 k6 的 2xx 不足以证明抽奖正确。
- 25 RPS × 60 秒是探索短测，不是正式容量。当前正式稳定档退出标准是同配置 300 秒、三个全新证据文件复测，并满足延迟/错误/排空/业务账本门槛。

### 受控对照结果

每条配置目前只有一轮 60 秒探索；除表中所列变量外，目标到达率与时间相同。短测的边界迭代允许最多多出一个请求，所以 1501 对计划的 1500 并不等于生成器丢压；仍需在多轮中观察稳定性。

| 单轮配置 | 实际受理 | 入口 P95/P99 | 受理→终态 P95 | 排空与对账 | 短测判断 |
| --- | ---: | ---: | ---: | --- | --- |
| 消费并发 1、Outbox 间隔 5 秒 | 1501 | 30.3 / 36.5 ms | 127.5 s | 120 秒内仍有 321 条 pending；未排空 | FAIL；同时旧生成器阈值将边界多出的一次计为退出失败 |
| 消费并发 1、Outbox 间隔 1 秒 | 1500 | 35.8 / 49.1 ms | 36.5 s | 120 秒内排空；业务对账通过 | FAIL；端到端 P95 超过 5 秒目标 |
| 消费并发 2、Outbox 间隔 1 秒 | 1501 | 74.2 / 129.3 ms | 11.3 s | 120 秒内排空；业务对账通过 | FAIL；生成正常，但端到端 P95 仍超目标 |
| 消费并发 4、Outbox 间隔 1 秒 | 1501 | 37.8 / 56.0 ms | 2.65 s | 120 秒内排空；业务对账通过；无 dropped | PASS（仅 60 秒短测） |

### 能得出的结论与不能得出的结论

1. **异步入口快不代表处理能力足够。** 入口大约几十毫秒，但同步受理后，业务结果可能要等几十秒甚至超过两分钟；必须同时看 admission 与 terminal latency、积压年龄和排空情况。
2. **Outbox 固定延迟会影响通知被发现的节奏。** 同为单消费者，间隔从 5 秒改为 1 秒后，本轮观察到端到端 P95 从约127.5秒降到36.5秒并排空。这是强烈的调度等待信号，但单轮本机数据不足以证明它是唯一根因。
3. **消费者并发可能提高服务速率。** Outbox 固定为1秒时，并发从1到2再到4，单轮 P95 依次约36.5秒、11.3秒和2.65秒。该趋势与分区消费并行相符；不过数据库竞争、JVM 调度和单机资源也会影响结果，必须复测，不能仅凭一组点估计最优并发。
4. **短测 PASS 不是“系统容量=25 RPS”。** 当前 25 RPS、60 秒、单主机、单 Kafka broker、一个用户/一个活动，是选候选档位的探索证据；没有证明多机扩容、故障期间容量或公网生产能力。
5. **本轮只改隔离 benchmark 参数。** 1 秒 Outbox 间隔和消费者并发4通过测试脚本覆盖，仅用于比较，不等于已经更改产品默认配置。要推广为生产参数，需额外观察数据库连接/锁等待、Kafka lag、队列年龄、错误率，并验证部署规模与恢复行为。

**5 分钟复测结论：** 候选配置 `25 RPS × 300 秒、Outbox 1 秒、消费者并发4` 三轮独立复测全部通过：R1计划7500、实际受理7501（允许一个边界迭代），R2/R3各受理7500，三轮均无 dropped；入口 P95/P99 分别为40.10/98.68ms、33.71/44.31ms、34.41/56.38ms，受理至终态 P95 分别为3.04秒、2.52秒、2.57秒；三轮均在120秒内排空并通过业务对账。端到端 P95 中位数约2.57秒，范围2.52～3.04秒。场景为一个合成用户、一个活动、奖品库存1，仍是同机单节点实验。

### 50 RPS×60 秒边界探索：失败也要如实保留

首次单机、单用户/单活动、消费者并发4、Outbox 1秒、池10的 50 RPS×60秒诊断尝试3001次，2996次受理，5次因 `MYSQL_CONNECTION_POOL_PRESSURE` 被保护性拒绝，0 dropped；入口 P95/P99 137.9/372.8ms、终态 P95 56.0秒、退出后57.8秒排空、最老年龄58秒。之后池20/消费者4、池20/消费者8、20用户/10活动/总库存10的同到达率诊断均未达到终态延迟门槛；多活动配置两轮终态 P95 约51.9和50.7秒，最终业务账本均正确。终态延迟样本包含预热请求。

这是“请求被保护性接受/拒绝”与“异步工作按目标时延完成”两件不同的事。最后一轮每5秒采样显示处理约26次/秒，50 RPS 到达时队列积压最高约1447条；Hikari 活跃峰值8/20、等待0，锁等待点采样最高1，事务内各成功 DB 段均值约1～3ms。Campaign JVM CPU采样均值约59%单核、峰值144%单核。数据不支持把慢 SQL或连接池饱和直接认定为唯一瓶颈，但也未覆盖足够细的 Kafka offset commit/Outbox阶段分布。性能门槛仍失败，当前暂停升压；下一步先审阅并观测 Outbox→Kafka 确认和 listener 消费后的同步提交等待，再挑一个可证伪原因做优化。完整记录见 [`docs/baseline/README.md`](../baseline/README.md) 与原始[分段报告](../baseline/draw-queue-arrival-50rps-60s-relay-1s-consumer-4-20users-10campaigns-pool20-segments-2026-09-29.json)。

## 四、这项优化的面试回答与追问

### “你怎么证明 Kafka 队列处理得过来？”

> 我没有把请求返回 202 或 2xx 当作处理完成，而是用开放模型持续产生负载，分别测请求受理和受理到业务终态延迟，并统计 dropped、队列积压/最老年龄。停止发压后还检查能否排空，并对账 MySQL 队列、抽奖、库存、Outbox 和 Worker 账本。短测里入口 P95 只有几十毫秒，但单消费者时端到端 P95 仍超过36秒，说明只看入口吞吐会掩盖积压。

### “你具体优化了什么？为什么没有直接调大线程池？”

> 先基于代码确认 Outbox Relay 有固定调度间隔、队列 Kafka listener 并发可调，再用隔离实验逐步改 Relay 间隔和 listener concurrency。25 RPS 三轮通过后，我没有把它外推成容量；50 RPS 诊断中连接池翻倍、消费者并发翻倍、多活动分散都没有达到时延目标。后来补了 Hikari/锁等待、JVM、队列处理和数据库分段计时：处理速率约26次/秒，但连接池不等待、DB段均值约1～3ms，因此下一步看 Outbox/Kafka确认与等待路径，不先加线程或改 SQL。任何优化还要用同配置业务对账验证。

### “Kafka 保证不丢消息或只处理一次吗？”

> 不能把 Kafka 的投递语义说成业务 exactly-once。我们用同事务 Outbox 覆盖数据库提交与发布之间的双写窗口；发布可能重复，消费也按至少一次的现实来设计，业务状态迁移、唯一键/幂等键和租约 fencing 保证重复消息不重复扣库存或生成业务结果。消息是通知，MySQL 是最终判定依据。

### “Redis、Kafka、MySQL 各自负责什么？”

> Redis 做短路径流量保护和限流；Kafka 做异步事件传递、缓冲和消费者解耦；MySQL 保存最终业务状态并通过事务、条件更新/锁和幂等约束保证库存及结果正确。三者解决不同问题，不能用 Redis 替代库存事务，也不能用 Kafka 作为最终中奖事实。

### “为什么测试只在一台机器？结果能不能放简历？”

> 这是个人项目的隔离本机基准，生成器和服务共享 CPU/网络/磁盘，监控本身也有成本，所以我只报告环境、时长、参数、原始文件和限制，不把结果外推线上。25 RPS 通过了同配置300秒三轮复测；50 RPS 多轮都未达性能门槛：第一次有5次连接池保护拒绝，后续调大连接池、提高消费者并发和增加活动数仍有约50秒终态 P95，处理速率约26次/秒。最终排空和账本正确不等于时延达标。我保留失败并停在当前边界，下一步用更多 Kafka/Outbox阶段观测定位。多 Broker、高可用和生产容量仍需不同环境与测试设计。

## 五、Agent 框架选择：怎么讲才不空泛

仓库里的 Python Agent 是 **FastAPI + LangGraph StateGraph + 项目自己的应用级 Harness**。图目前控制 `model → tools → model/end` 循环；读写权限、工具白名单、模型/工具次数、时限/输出预算、身份委托、MySQL 持久 Run、取消/租约/SSE 和 RAG 引用复核主要由项目代码实现。LangGraph 的 checkpointer 未被当作 RunStore，也没有宣称模型步骤跨进程自动续跑。

- **LangGraph** 适合需要显式控制流、分支和可测试节点的工作流。仓库 `uv.lock` 当前解析为 LangGraph 1.2.12、LangChain Core 1.6.5（2026-09-29 核对；LangGraph 官方 release 也列出1.2.12），不是老版本；`pyproject.toml` 的兼容范围是 `langgraph>=1.0,<2`，精确复现由 lock 文件保证。[LangGraph 官方发布记录](https://github.com/langchain-ai/langgraph/releases)。但当前业务图很小；单独说“用了 LangGraph”不是竞争力。官方持久化/中断能力需要实际启用 checkpoint 等条件，本项目不能把这些框架功能当成已落地能力。
- **DeepAgents** 是建立在 LangChain agent loop/LangGraph 生态上的更 opinionated Harness，附带规划、文件系统、子 Agent、上下文整理等能力。对需要长任务自主研究/编码的通用 Agent 有价值；PrizeFlux 的用户助手刻意保持只读、窄工具面，直接采用完整默认能力会扩大权限面，收益需证明。[DeepAgents 架构说明](https://github.com/langchain-ai/deepagents/blob/main/libs/ARCHITECTURE.md)
- **AgentScope 2** 是更完整的 Agent 框架/服务方案，官方描述包含 Agent、Agent Service、多租户会话、团队协作、持久化、RAG、工具权限和部署能力。新建多 Agent 服务时值得认真评估；迁移本项目则需确认它与现有 Campaign JWT 委托、MySQL RunStore、任务租约、SSE 和 Java 产品边界如何共存，不能只因组件多就替换。[AgentScope 官方仓库](https://github.com/agentscope-ai/agentscope)
- **DeepSeek Harness** 当前是 Node/TypeScript 与 Cordis 插件生态的独立产品，官方仓库标注 developer preview、API 可能破坏兼容；它适合研究插件化 Harness 设计或作为单独学习原型，不是当前 Python 服务的低成本替代。[DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)
- **直接使用模型 SDK** 只解决供应商请求、结构化工具调用等底层协议；它不自动提供任务状态、持久会话、授权、取消、审计、预算或恢复。项目的 `ModelPort`/provider adapters 已把模型协议隔离，但执行生命周期仍需上层实现。

**专业判断：** 暂时保留 LangGraph，不进行仅为追逐热门项目的迁移。简历描述应是“基于 LangGraph 编排、构建面向业务的受控 Harness”，而不是“自研 LangGraph/Agent 框架”。如果要证明选型有竞争力，下一步应以同一组权限/工具/取消/重放/拒答/eval 用例，做一次轻量 raw-SDK loop 与当前 LangGraph runtime 的对照；如有明确多智能体/服务治理需求，再评估 AgentScope 2 或 DeepAgents。该对照尚未实现，不能写成已完成。

## 七、复现与证据索引

### 2026-09-30 优化案例：先定位Relay吞吐上限，再做单变量验证

**现象：** 50 RPS合法负载全部受理，但受理至终态P95仍约50.67秒；此前扩大连接池、消费者并发和活动数没有明显改善。入口响应快不代表后台处理能力足够。

**定位过程：** 对Kafka发送拆分enqueue/ack-wait计时，采集每个consumer的commit指标，并异步缓存group committed lag。45.3～95.1秒发布增量26.47条/秒，ack等待均值2.53ms，Outbox单条发布均值17.61ms；lag样本0～18、发送与完成累计数接近。源码每批最多50条串行投递，批次结束再等待1秒。粗略估算 `50/(50*0.01761+1)≈26.6条/秒` 与实测一致，因此先验证批间等待，而不是直接改Kafka确认语义。

**最小实验：** 新增仅隔离benchmark可用的毫秒延迟参数，保留旧秒参数，拒绝同时传两种单位；结果保存有效延迟与构建hash。同样50 RPS×60秒、20用户/10活动/池20/consumer4/总库存10，只把等待1秒改成100毫秒。生产默认值、串行发送、每批50条、租约、ack与事务协议不变。

**第一轮结果：** 100毫秒档3000/3000受理、0 dropped，入口P95=43.89ms，终态P95=14.159秒（原1秒档50.672秒），峰值业务pending从1432降至480；含预热3150条全部终态，10条中奖/Worker成功，库存0，无重复。仍未达到5秒门槛，整体性能FAIL。发布与完成累计数开始分离，group lag缓存样本最高400，说明消除发布侧限制后，消费侧成为新的候选限制。仅各一轮60秒配置对照，不是代码并发优化成果，不等于稳定容量。原始记录：`docs/baseline/draw-queue-arrival-50rps-60s-relay-100ms-r1-2026-09-30.json`。

**第二轮结果：** 固定100毫秒，仅consumer4→8，50 RPS×60秒本机单轮PASS：3001/3001受理、0 dropped，入口P95/P99=61.81/93.22ms，终态P95=4.439秒，峰值业务pending196，停止流入120秒内排空。含预热3151条队列/结果/DrawQueued SENT一致，10次中奖与模拟履约成功、库存0、无重复。原始记录：`docs/baseline/draw-queue-arrival-50rps-60s-relay-100ms-consumer-8-r1-2026-09-30.json`。从原1秒/consumer4的50.672秒到候选4.439秒仅是两个参数分步探索的单轮对照，不宣称生产提升比例或稳定吞吐；50 RPS×300秒三轮与新候选故障演练仍待做。入口时延略升也保留，不能只报终态改善。

**讲解顺序：** 先说明可靠事务/幂等不变量，再展示“受理快、终结慢”；用分段指标发现发布限制，降低批间等待后观察积压转向消费侧，再调消费者。重点是瓶颈随改动迁移，扩容效果取决于当前限制，而非“线程越多越好”。

**稳定性反证（同日）：** 100ms/consumer8的50 RPS×300秒第一轮FAIL：15001/15001受理、0 dropped，入口P95/P99=57.33/92.41ms，但终态P95=29.884秒，峰值pending1241，停止流入后约30.12秒排空。含预热15151条全部结果/通知对账，10次中奖/履约成功、库存0、无重复。101.2～294秒负载窗口发布47.57条/秒、Outbox单条发布均值18.56ms，lag缓存样本最高18。不能把60秒PASS保留为“稳定50 RPS”亮点；不重复已失败配置凑三轮，下一隔离诊断只改等待100ms→10ms。原始记录：`docs/baseline/draw-queue-arrival-50rps-300s-relay-100ms-consumer-8-r1-2026-09-30.json`。

**项目八股：为什么要长测？** 当服务平均处理速率略小于到达率时，短测可能暂时满足延迟门槛，长时间积压会持续增长。可靠性正确与容量充足是两个独立结论；需要开放到达率模型、终态时延、排空和业务对账一起验证。短测优化有效不代表目标已经完成。

**历史反例：** 10ms/consumer8、50 RPS×300秒单变量对照更差，终态P95=72.756秒，15001全部受理、最终对账正确。负载窗口Outbox发布均值24.72ms，ack仅1.50ms，发布约39.12条/秒。这不能证明轮询压力是唯一原因，但足以否定“等待越短越快”的简单结论。随后新增RECLAIM/CLAIM/MARK_SENT/重试/死信分段，并发现consumer8候选仍会在5分钟长测积压；consumer12候选的后续三轮数据见下文。生产默认未改。

- **新增定位证据：** 完整Spring新分段烟测PASS。串行50 RPS×60秒诊断窗口40.4～93.3秒中，markSent 2640次、累计40.59秒、均值15.37ms；claim 59次均值20.55ms（每批，不是每事件），reclaim 58次均值1.18ms；同窗口publish均值17.34ms、broker ack均值1.82ms。支持先缓解逐条状态回写的串行等待，而不是宣称Kafka确认慢或直接改AckMode。repository计时包括连接/SQL/提交等待，未证明某条SQL或fsync是唯一根因。
- **工程实现：** 并发参数默认1、可选2～8；独立 `BoundedOutboxDispatcher` 固定线程和有界队列，每轮只claim一波（最多parallelism），不要先领取50条让后续事件排队超出租约。逐事件确认后按token回写；失败仅释放/死信该事件。整波join后再领取；15秒等待上限，并发lease至少30秒。timeout/中断停止本实例后续领取、取消工作；不宣称能强杀JDBC，仍由旧token围栏和租约恢复保护，需重启/其他Relay回收。默认串行和生产delay保持不变。

同候选的首次Kafka故障演练揭示另一问题：Relay轮询100ms时，失败事件立即重新可领取，在Broker重启窗口内用完3次尝试并死信。原因是旧 `release` 只清租约，没有推迟 `available_at`。加入数据库持久化指数退避（2秒起、30秒封顶）后，22项定向测试通过，真实MySQL/Kafka重试记录在恢复后 `SENT:3`；队列在Kafka不可用时仍 `QUEUED:0`，Broker约8.09秒恢复，通知确认后才启consumer，最后完成一条抽奖、库存归零。此修复不需迁移，长故障超过最大尝试仍需死信处理。首次失败未生成JSON，当时脚本异常分支仅输出脱敏诊断；该证据缺口也已如实注明。

**面试追问：**

- 为什么不直接增消费者？若消息还在MySQL Outbox等发布，新增consumer无法消除发布侧瓶颈。
- 为什么不是broker ack慢？该窗口ack均值只有2.53ms，但这不能代表尾延迟；要同时看总发布成本、批间调度和业务队列，而非只看一个均值。
- 为什么不立刻并发发送？会新增在途上限、超时但已送达、关闭与旧租约回写窗口。先用既有配置检验假设，必要时才增加有界并发。
- 为什么100毫秒不是无成本？空队列时claim/reclaim查询会更频繁，可能增加数据库负担；必须观察资源、空载成本和故障恢复，短测有效也不能立即称生产配置。
- 为什么保留失败实验？它们解释选型过程，防止把偶然测量或框架堆叠包装成性能成绩。

这个案例的亮点首先是可复现的定位方法与保持业务不变量的取舍；收益只有实际对照通过后才能进入简历数字。
